Startup Performance Analysis Report

Target: Low-end devices (e.g., TCL TVs)

Focus: SerenityApplication.kt and initialization logic.

Executive Summary

The application performs several heavy operations on the Main Thread during onCreate(). On high-end devices, these might be negligible, but on low-end Android TVs (which often have slow storage and limited CPU), they can cause significant startup delays (black screen or slow UI rendering).

1. Critical Bottleneck: Media Codec Logging High Impact

Location: SerenityApplication.kt → MediaCodecInfoUtil.logAvailableCodecs()

Analysis

You are calling MediaCodecInfoUtil.logAvailableCodecs() synchronously in onCreate(). Inside this utility, you instantiate MediaCodecList(MediaCodecList.ALL_CODECS). Querying the underlying hardware drivers for all available codecs is an extremely expensive operation on Android TV devices. This can block the main thread for hundreds of milliseconds or even seconds.

Recommendation: Move this to a background thread (e.g., using Dispatchers.Default) or remove it entirely from the release build. 
// Example fix
ProcessLifecycleOwner.get().lifecycleScope.launch(Dispatchers.Default) {
    MediaCodecInfoUtil.logAvailableCodecs()
}

2. Heavy Initialization: Joda-Time Medium Impact

Location: SerenityApplication.kt → init() → JodaTimeAndroid.init(this)

Analysis

JodaTimeAndroid.init(this) loads time zone data from assets/resources. While optimized, this involves disk I/O and parsing, which adds latency to the startup sequence.

Recommendation: If Joda-Time is not needed immediately for the first frame render, consider moving this to a background thread or a lazy initialization block.

3. Disk I/O on Main Thread: Preferences & Cache Medium Impact

Location: SerenityApplication.kt → onCreate()

Analysis

  • setDefaultPreferences(): Calls PreferenceManager.setDefaultValues(...). This reads an XML file from the APK and writes to the shared preferences file on disk if it doesn't exist. This is a blocking I/O operation.
  • ExoDatabaseProvider & SimpleCache: Creating these objects involves database and file system interactions. While SimpleCache often initializes its index asynchronously, setting up the ExoDatabaseProvider can still incur checking/opening the SQLite database on the main thread.
Recommendation:
  • Preferences: setDefaultValues has a readAgain parameter. Ensure it is false (it is currently true in your code). Changing this to false prevents re-reading if already set. Even better, run this off the main thread.
  • ExoPlayer Cache: Initialize the SimpleCache lazily (e.g., using a lazy delegate) so it is only created when the video player actually needs it, rather than at app startup.

4. Dependency Injection Overhead Low/Medium Impact

Location: SerenityApplication.kt → init() → inject()

Analysis

The Toothpick.openScope(...).installModules(...) call constructs your object graph. While generally fast, the SerenityModule creates a new OkHttpClient.Builder().build(). Building OkHttpClient can be slightly expensive due to SSL context initialization.

Recommendation: Ensure OkHttpClient is lazily instantiated or strictly a singleton reused effectively.

Action Plan

To immediately improve startup time on TCL TVs:

  1. Wrap MediaCodecInfoUtil.logAvailableCodecs() in a coroutine (Dispatchers.Default).
  2. Move JodaTimeAndroid.init(this) to a background coroutine if safe to do so.
  3. Lazily initialize SimpleCache instead of creating it in onCreate.
